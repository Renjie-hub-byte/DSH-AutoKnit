# AutoKnit

**把 PRD 丢进来，它自己拆任务、派 Agent、验收、递归拆分——用更少的 token，产出更稳定、更好维护的代码。**

AutoKnit 是介于「跟 Agent 一步步聊太累」和「企业级重框架太贵」之间的开源分治执行框架。它不做"总指挥"烧上下文：**程序负责调度（0 token），LLM 只出智力**。你只审一眼规划，最后合一次代码。

> **实测**：7,000 行级任务，AutoKnit 冷启动 **最省（749K token）、最快（37 分钟）、测试密度最高（26.4/千行）**，比交互式单 Agent 省 19%、比 lh-harness 省 41%。完整对比见[第二节](#二实测数据2026-08-3031同一台机器同一口径)。

> 运行底座是 [dsh](docs/quickstart.md)（**DeepSeek harness**，下文简称 dsh）——负责会话与模型调用；AutoKnit 负责拆分、派工与验收。对比参照系 [lh-harness](https://github.com/)（**Long Horizon Harness**，优秀的企业级开发框架）同样以 codex 为执行者，本 README 部分数据引自与它的公平对比。

---

## 一、它解决什么问题

**痛点：Vibe Coding 开发者费时费力费心，不知道怎么安排和架构。**

| 你现在的做法 | 难受在哪 |
|---|---|
| 跟自己的 Agent 一步步聊、一步步修 | 同一件事反复说，上下文越滚越大 |
| 丢给交互式编码工具（大任务） | 任务超过约 1000 行后，单会话编排成本失控，交付偏薄 |
| 用开源重架构保质量 | 反复灌输上下文维持状态，消耗巨大 |
| 上线后改需求 / 修 bug | 改 1 个点联动好几个模块，返工 + 回归反复烧 token——**开发 5 块钱，拉扯和维护 100 块钱** |

AutoKnit 补的是这个空档：**用工程和契约替代"反复沟通"，让 LLM 只贡献智力。瞄准 1,000–10,000 行规模——省的不只是代码产出本身，更是开发过程的反复拉扯、和后期维护的重复返工这些隐形成本。**

### 修改实验：四份交付物接同一道修改题（给 merge 加 --dry-run）

真实场景还原：你让 Agent 改个功能，它会先琢磨"要动哪几个文件"，然后动手。**如果它的预估和实际差距大，就会改这个漏那个——轻则多轮返工费心费力，重则带着没发现的隐藏问题上线**。所以我们测：给四份独立生成的交付物（AutoKnit 两版 / lh / 交互式）同一道修改题，用 codegraph 先记录"结构预测的影响面"，再实测实际改动，对比偏差。

| | AutoKnit（dogfooding 版） | AutoKnit（冷启动版） | lh-harness | 交互式单 Agent |
|---|---|---|---|---|
| 消耗（raw，含缓存）* | 770,150 | 628,552 | 802,329 | **381,670** |
| 预测 vs 实际偏差 | **-1**（预测 5 实际 4） | **+1**（预测 4 实际 5） | +3（预测 3 实际 6） | +2（预测 3 实际 5） |
| 测试存活 | **58/58** | **29/29** | 39/39 | 19/19 |
| 越界读取 | 0 | 0 | 0 | 0 |

> ⚠️ **口径说明**：本表是全文唯一的 raw（含缓存）口径——修改实验执行时该交互式工具只记录含缓存的总消耗，无法拆分。**四方同口径，相对比较有效；绝对值与其它表格（计费口径）不可直接换算。**

### 从数据读出的四句话

**一句话总述：AutoKnit 用更省的 token，交付更可维护、更可靠的代码——省钱不是靠少干活，是靠把编排和验收变成 0-token 的程序，让每一分 token 都花在真正的产出上。**

1. **小任务（≤1,000 行）：交互式工具仍最便宜**（36–52K，AutoKnit 62–304K）——这就是为什么我们把甜点区下限设在 1,000 行：单会话无编排开销，小任务它就是最优解。**但任务一旦有跨模块依赖链（如 m02 三模块），AutoKnit 就反超（303K vs 交互式 507K，省 40%）**。
2. **大任务反转**：7,000 行时 AutoKnit 冷启动**最省（749K，比交互式 -19%、比 lh -41%）、最快（37min vs 4.5h）、测试密度最高（26.4/千行）**。交互式单会话形态在规模面前上下文膨胀（未缓存输入 861K 全花在读新内容上）。
3. **交互式的便宜不含审计**：它的计费里没有独立验收。我们事后给三份交互式交付物做同等强度的清单审计花了 559K（约 19 万/份）——**补齐审计后，交互式的真实成本 = 生成 + 审计**。AutoKnit 的 auditor 是内置的，报价即含验。
4. **改动影响面可预测、可报价**：Agent 改代码的固有流程是「先读结构 → 预测要动哪些文件 → 动手改 → 跑测试」。AutoKnit 的交付因为**分治 + 模块化 + 契约边界**，agent 读到的结构就是清晰的模块拓扑——实测预测偏差 ≤±1，最大程度避免「修改不完全、改一处连带改一片、改不彻底带问题上线」这三类返工事故。**测试密度 26.4/千行是对照的 3 倍以上，是"可靠"的直接证据——同样的行数，AutoKnit 交付的代码有超过 3 倍的测试护航。**

### 甜点区（诚实边界）

| 任务规模 | 推荐 |
|---|---|
| ≤500 行 | 直接用交互式工具，随手实现随手改，别上框架 |
| 500–1,000 行 | 都可以；交互式更快，AutoKnit 更厚 |
| **1,000–10,000 行** | **AutoKnit 的靶心区**——拆分、契约、验收开始产生复利 |
| >10,000 行 | 理论可行，尚未系统验证 |

## 三、核心机制（架构原理）

```
                PRD
                 │
        ┌────────▼────────┐
        │     planner      │  按耦合拆分：高内聚的聚成一个模块
        └────────┬────────┘   + 首任务详细清单 + 模块间契约
                 ▼
        ┌────────▼────────┐
        │     executor     │  独立会话，只为本模块负责
        └────────┬────────┘
                 ▼
        ┌────────▼────────┐
        │     auditor      │  逐条核对验收清单 + 程序采证
        └────────┬────────┘
                 │ 剩余模块还大？
                 ▼ 大（阈值可调，建议 ≈1000 行）→ split 递归拆分
                   小 → executor 续做收官
                 ▼
            全部完成 ✅
```

1. **planner 按耦合拆分**：高耦合的代码聚成同一个模块（改 A 必改 B 的就该在一起），模块间只通过**数据契约 + 接口契约**说话，不读对方源码。
2. **executor 执行 + 热续做**：独立会话只干一个模块；剩余体量小于阈值时**不拆新块，由当前 executor 续做收官**——它刚做完前一块，代码上下文还热着，省 token 且质量连贯。
3. **auditor 验收**：独立角色，验收清单逐条核对 + 程序采证（codegraph / semgrep），不过就打回。
4. **split 递归**：剩余体量超阈值才继续拆，每块"一口吃完"。
5. **拆分粒度是最大成本杠杆，也是质量与开销的平衡点**：同一任务不同粒度实测成本差 4.6×（63K–336K）。我们在质量和开销之间取的平衡阈值是 **约 1000 行 / 单个 executor 任务量**——超过就递归拆小（每块小上下文更聚焦），没超过就让当前 executor 续做收官（上下文还热着，省 token 且质量连贯）。这个阈值由配置项 `split_exit_threshold` 控制（默认 1000，可按任务特性调）。

### 打回与回人（全自动的边界，说清楚你什么时候需要出场）

auditor 打回 ≠ 推倒重来。修复永远是**原地继续**：模块产物保留，executor 下一轮带着【前轮反馈】（上轮已做/待办）接着修；即使换 executor，也只是换人**接手已有进度**（进度快照 + 交接包），不从零开始。

打回后的升级链（默认配置，程序自动走完，全部失败才需要你）：

```
auditor 打回
  → 同一 executor 原地修（最多 2 轮，REVIEW 定位到待办）
  → 换一个 executor 接手续修（1 次）
  → 递归 split：把做不完的模块拆成更小块
  → 升级模型兜底（flash → pro）
  → 以上全部失败才 needs_human，真人接管
```

两类例外不耗轮次直接回人：失败根因是**上游/契约**（重试无意义，先修依赖），或**环境问题**（限流/断网——限次退避重试 3 次，不换人白换）。

dashboard 的「待决策项」只有两种，都不是代码级小决策（代码层 auditor 已逐条采证判掉）：
- **人工验收项**：GUI 效果 / 真实场景 / 体验——框架验收不出来的维度。代码层已全绿，列出来交你和外部 AI 复核。
- **需要决策的模块**：自动化到顶的模块，附根因（交付问题 / 环境问题 / 契约问题 / 卡死）和 A 放弃 / B 改方案 / C 暂停 / D 自定义 四个选项。

### 契约长什么样

模块间不共享代码，只共享形状。每个模块的任务书里带契约文件（自动生成；你也可以在 PRD 里显式声明，planner 会尊重你的声明）：

```yaml
# contracts/m01-task-state.yaml（示例）
interface:
  dsh.task.list:
    direction: F→R
    returns:
      tasks: "List[TaskSummary]"   # 按 urgency 降序
      task:
        id: str
        stage: planning|executor|auditor|rejected|reassigned|needs_human|done
        modules: "List[{id: str, stage: str, rejected_count: int}]"
data:
  snapshot.json:        # 本模块只读的上游文件
    run_id: str
    phase: str
  dispatch.jsonl:       # 事件流，append-only
    events: "List[{seq: int, type: str, payload: dict}]"
boundary:
  may_read: [contracts/, shared/]
  may_write: [modules/m01/]
```

executor 的全部世界就是这份契约 + 自己的模块目录——它不需要、也不被允许了解全局。

### 为什么保质保量还省

**AutoKnit 省 token 的秘诀不是"让 LLM 少干活"，而是"让 LLM 只干它最擅长的事"——写代码。所有编排、校验、依赖、复用指引，都由程序在 0 token 的调度层完成，LLM 用少量智力，干更高质量的活。**

- **0-token 程序调度**：runner 是程序不是"总指挥"，LLM 只出智力。大任务实测中 AutoKnit 的编排层成本为 0，把全部 token 花在真正产出上。
- **缓存友好**：前缀冻结纪律 + 模块独立会话，缓存命中 94–98%。
- **确定性的工位**：契约、接口、边界由程序预先加工好塞进任务书，executor 的工具调用 100% 花在写代码上，探索性调用为零。
- **上游能力摘要（UCD）**：模块完成后程序 AST 提取公开接口，0 token 注入下游【前·上游】——下游直接复用上游已实现能力（m03 复用 m02 的 summary），不重写、不探索（实测该模块省 32%）。
- **auditor 程序采证**：pytest/semgrep/越界由程序预跑注入采证层，auditor 只抽查不全量——审计成本占比从 34% 降到 22-28%，且逐条采证不漏查。
- **依赖一次装齐**：任务声明的 python_packages 由 bootstrap 聚合安装（含 120s 超时兜底），executor 不再现场装或自造轮子。
- **便宜模型 + 低思考档可用**：实测 deepseek-v4-flash（flash 档、思考 low）全程产出厚交付——架构把"安排和架构"从 LLM 肩上拿走了。

## 四、怎么用

### 流程

现在的 Agent 都已经具备「追问补充、把模糊需求聊成完备 PRD」的能力——这个前置沟通通常 **3 轮对话**就够。之后把它交给 AutoKnit，省去的是后面几小时的反复拉扯、和上下文膨胀导致的信息丢失：

```
1. 跟你的 Agent 说需求            ← 你只出主意
2. 你的 Agent 追问补充，产出完备 PRD  ← 通常 3 轮对话
3. autoknit plan-only <任务目录>   ← 先审规划：几个模块、各多少行、契约清单（不执行不花钱）
4. autoknit run                    ← 拆/派/写/验/续做/递归，全自动
5. 拿到 modules/ 模块代码 + 合并说明
6. 你的 Agent 对照合并说明，一轮合并  ← 你只审一眼
```

### 依赖（从零开始）

1. Python 3.11+、git、npm
2. `pip install autoknit` —— 一键装好 `autoknit` 命令（框架已打包内置，含 fw-protocol / fw-scaffold / 数据桥）。源码方式：`git clone https://github.com/Renjie-hub-byte/DSH-AutoKnit.git && cd DSH-AutoKnit && bash install.sh`
3. 安装 [dsh](docs/quickstart.md 附录 A)（DeepSeek harness，`npm install -g @deepseek-ai/dsh`）并登录，或在 `~/.autoknit/config.yml` 指定你的 dsh 路径与凭据位置
4. `autoknit doctor` —— 一键体检：dsh 二进制 / 凭据 / 模型路由 / 面板连通性，缺什么告诉你怎么装

### 常用命令与参数

| 命令/参数 | 意义 |
|---|---|
| `autoknit plan-only <dir>` | 只跑 planner：产出 task.yaml（模块拆解 + 契约），不执行、不花执行 token；供人审后用 `run` 接续 |
| `autoknit run [--resume]` | 全流程执行；`--resume` 从 checkpoint 接续（崩溃/中断后不重复规划）。续做阈值由配置项 `split_exit_threshold` 控制（默认 1000 行） |
| `--executor-model <模型>` | 执行模型可换（实测 flash 档即可产出高质量交付） |
| `autoknit dashboard` | 可视化面板：模块进度链、各角色耗时、token 消耗（输入/输出/缓存）、待决策项（人工验收项 / 回人模块及根因，见「打回与回人」）。install.sh 已装好数据桥；dsh 侧配套人可见任务流程的 dashboard 插件，插上即用；接口全暴露，你可以自己做自己喜欢的界面 |
| `autoknit doctor` | 环境体检：缺什么、怎么装，人话报错 |

### 关于合并

`autoknit merge` 是**纯程序、零 LLM** 的机械合并：产出①按依赖拓扑归位的目录骨架，②每个模块的目标接口文件，③跨模块 import 接线，④四类冲突清单（同名 / 命名不一致 / 接口签名出入 / 需语义融合——每条标注"需人工定夺"）。实测：合并说明交给 Agent，**一轮会话即可完成合并**，剩下语义级融合的部分清单里标得清清楚楚。

## 五、失败模式与防护（都是我们踩过且已修复的，希望你别再踩）

| 我们踩过的坑 | 现状与防护 |
|---|---|
| 提示词"（如有）"制造不确定性 → executor 失去边界自行探索（实测多烧 80K/轮） | ✅ 已修复：runner 程序侧判断，该给的一定给，不存在的绝不提 |
| 拆分粒度失当 → 成本放大 4.6× | ✅ 已防护：plan-only 先审拆解 + split 递归 + 续做收官 |
| final_block 剩余被静默吞掉 | ✅ 已修复：split 单块语义重构（BUG-20260829，留痕可追溯） |
| 各模块单测全绿、一拼就断（契约不一致 / CORS / 端点用错） | ✅ 已防护：契约对齐 + merge 冲突清单 + 真人 or agent集成验收 |
| venv 状态漂移 / 解释器死链 → 启动静默崩 | ✅ 已修复：bootstrap 试运行校验 + 预检人话报错 |
| 长任务被系统睡眠冻结（macOS 合盖） | ✅ 已防护：运行时自动包裹防睡眠 + QUICKSTART 提示 |
| 任务声明的依赖没装（zstandard 等）→ executor 缺包被逼自造 | ✅ 已修复：bootstrap 聚合 task.yaml 的 python_packages 安装（120s 超时兜底，装不上写「已知风险」不阻塞） |
| 「缺依赖优先标准库」歧义 → executor 自造解码器（zstd 纯 Python 884 行，曾 293K/30min） | ✅ 已修复：工具红线（禁 web_search/curl 下载/自实现解码器；zstd 直接 `zstd -d -c`） |
| 上游信息断供 → 下游重复实现（m03 重写 m02 的 summary 138 行） | ✅ 已修复：UCD 上游能力摘要（模块 done 程序 AST 提取接口，0 token 注入下游【前·上游】） |
| 引导「复用」但没给 import 路径 → 下游 sys.path hack 翻上游源码（m03 曾贵 16%） | ✅ 已修复：UCD 复用指引（直接 import）+ PYTHONPATH 注入 + 防联想纪律 |
| auditor 通读全部源码 + 重跑测试 → 占 34% 成本 | ✅ 已修复：程序预采证（pytest/semgrep/越界）+ 抽查不全量（占比降到 22-28%，逐条采证不漏查） |

**为什么敢承诺"强壮"**：我们发现 AI 的容错是"清单驱动"的——PRD 点名的场景（原子写、畸形输入、确定性错误码）全部经住了对抗性注入实测；PRD 没点名的（并发竞态、链接逃逸）是所有 AI 工具的共同盲区。所以 AutoKnit 的对策不是祈祷模型发挥，而是把标准鲁棒性清单由**程序硬编码进每个任务书**，auditor 有据可查。（当然，随着模型能力提升，可能会有改观，但autoknit恒定在用同时代的低档次模型达到高档次模型的效果）

## 六、AutoKnit 不适合什么

- 几百行的脚本和一次性工具——杀鸡用牛刀，甜点区从 1,000 行开始
- 需要统一视觉审美的精细 UI 打磨——分治产出"能用且健壮"，像素级调优请用交互式工具
- 需求本身没想清楚的项目——契约驱动的前提是你能说清要什么（这正是第 1、2 步存在的原因，当然，任何开发都要如此，autoknit的效果在于，分治实现，后续迭代修改省心省钱省时）

> 说明：强全局状态、模块边界模糊这两类常被误以为不适合——其实正相反。强全局状态 = 高耦合，按耦合拆分时它本就该聚成一个模块（框架专门处理大模块，超阈值再递归拆）；边界模糊 = split 递归拆分的本职。所以它们不是"不适合"，是 AutoKnit 的用武之地。
